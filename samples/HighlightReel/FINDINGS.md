# HighlightReel findings

Where FunctionalLint helped, got in the way, or gave poor guidance while building HighlightReel ([spec](../../specs/highlight-reel.md)).

## Summary

- **Core size:** 619 lines in 9 files (466 not counting blank and comment lines). Cli: 34 lines. Tests: 162, all passing.
- **Lint errors hit while writing the app:** 2, both FP0005, both in a deliberate first draft of the JSON writer (#1). Plus 3 compiler errors (CS0029, my own type mistakes) that `heal.sh --check` reported in the same list. 0 auto-fixed. The other 8 core files were clean on their first check.
- **Lint errors hit by a deliberate probe:** I then wrote one throwaway file of the imperative code an agent tends to write for this app first (a `StringBuilder` EDL loop, a parser class, `throw` in a switch arm, `List<T>` parameters), to exercise the messages and fixes. It gave 21 diagnostics: FP0003 x6, FP0005 x3, FP0008 x3, FP0002 x3, FP0004 x2, FP0001 x1, FP0007 x1, FP0012 x1, plus CS1061 x1. heal.sh auto-fixed 12 (FP0003 x6, FP0004 x2, FP0005 x1, FP0008 x3), and one of those fixes created a new compiler error (#6). The file was then deleted.
- **Check time:** `heal.sh --check` took 4.6 to 5.2 s by its own clock, 6.3 to 7.3 s wall clock. The `dotnet run` start-up in heal.sh adds about 2 s. The Claude Code hook (which runs the built dll) took 5.3 s. A fixing run took 7.7 s (9.5 s wall).
- **False positives:** none in the real code.
- **Main lesson:** following `agents/AGENTS.md` from the start avoids nearly every lint error. The rules that did matter were the ones that *didn't* fire: the lint approved a fully imperative JSON writer and a builder mutated in a `ForEach` (#1, #2).

## What worked well

- Writing the functional way from the start, as `agents/AGENTS.md` says, made the lint nearly silent on real code: 8 of 9 core files were clean on their first check, with no false positives.
- `heal.sh --check` lists compiler errors alongside lint errors, so it's a single "am I done?" check.
- The fixes for FP0003, FP0004 and FP0008 in the probe were correct and kept the code's meaning (record, static class, `readonly record struct`, `IReadOnlyList<T>`).
- FP0012's message ("'ImmutableArray.Add' returns a new value and leaves the original unchanged. Use the result instead.") is exactly right for the most likely immutable-collection mistake.
- With CS8509 as an error and CS8524 off, `switch` over `OutputFormat` has no discard arm, so adding a format fails the build until every switch handles it.
- LINQ query syntax over `Result` (via samples/Functional's `SelectMany`) made multi-step validation read top to bottom, e.g. `from video in VideoLinks.Parse(link) from seconds in … from text in Label(label) select …`.
- Implicit conversions from `T` and `Error` to `Result<T>` keep conditionals short: `ok ? value : new Error(...)`.
- List patterns with slices on `ImmutableArray<string>` (`["add", .. var rest]`, `["--before", var v, .. var rest]`) made argument parsing small, total and loop-free.
