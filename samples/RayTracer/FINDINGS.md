# RayTracer findings

The numeric stress test: a ray tracer with no loops and no mutation in the hot path, built under FunctionalLint.

## Summary

| | |
|---|---|
| Core code | 8 files, 510 lines (367 excluding blanks and comments). Cli 54 lines. Tests 640 lines, 51 tests, all passing. |
| Lint errors in the real code | **0** over 15 per-edit checks. I had read AGENTS.md and the rule docs first and wrote to them, so the lint never fired on the app itself. |
| Lint errors in probes | To see the guidance, I wrote the imperative hot-loop code I would naturally reach for in a temporary file (since deleted). It produced 24 errors: FP0002 x10, FP0003 x7, FP0001 x3, FP0004 x1, FP0005 x1, FP0011 x1, FP0012 x1. A second probe produced CS8509 x1 and CS1061 x1. |
| Auto-fixed | 8 of the 24 (FP0003 x7, FP0004 x1), as 4 actual edits. |
| Check time | `heal.sh --check`: 4.4 to 5.2 s reported, 6.3 to 7.7 s wall. `heal.sh` (fix): 7.8 s reported, 9.7 s wall. |
| Render time | Sample scene, 320×240, 4 samples, Release: **0.42 to 0.45 s** on 1 thread and 0.26 to 0.28 s on 4. That is about 23 times under the spec's 10 s target. Warm, the render takes 72 ms and allocates 2.3 MB. Before optimising it took 162 ms and allocated 230 MB. |
| Output | 1 and 4 threads give byte-identical output. The optimised output is byte-identical to the first, idiomatic version. See `scenes/sample.png`. |

## Findings

| # | Rule or area | What happened | What you wanted to write vs what you had to write (short code) | Did the message tell you what to do? | Suggestion |
|---|---|---|---|---|---|
| 1 | Performance: LINQ in the hot path | The obvious nearest-hit query was about 20 times slower than its maths. `Intersection.Sphere` takes 10 ns and allocates nothing. `Nearest` over 3 shapes took 606 ns and allocated 536 B, from closures capturing `ray` and `Select`/`Concat` enumerators. The whole render allocated 230 MB, about 750 B per primary ray. | Wanted: `Spheres.Select(s => Sphere(s, ray)).Concat(...).Aggregate((Hit?)null, Closer)`. Wrote: `Spheres.Aggregate((Best: (Hit?)null, Ray: ray), static (acc, s) => (Closer(acc.Best, Sphere(s, acc.Ray)), acc.Ray)).Best`. Now 0 B and 224 to 266 ns. | n/a (no lint involved). FP0001 says "Use LINQ, Aggregate or recursion" with no word on cost. | Add a "hot loops" section to FP0001.md and AGENTS.md. | 2 | Performance: functional versus imperative | Even with no allocations, the functional style costs about 2 times. On the same 3 shapes, `Aggregate` with a static lambda took 261 ns, index recursion 158 to 169 ns and a `foreach` loop 114 to 117 ns (a reference copy outside the core). The cost is delegate calls plus copying a 120-byte tuple accumulator on every step. | n/a | n/a | Mention in the docs that `Aggregate` costs about 2 times a loop for small bodies. | 3 | Performance: lost short-circuit | `Any(s => Hit(s, ray) ...)` stops early but allocates a closure. The allocation-free `Aggregate` can't stop early, so `Blocked` went from 65 ns to 160 ns when the first shape blocks. `ImmutableArray` has no `Any(state, staticPredicate)`. | Wanted: `Spheres.Any(static (s, r) => ..., ray)`. Wrote: `Aggregate((Blocked: false, Ray, Distance), static (acc, s) => (acc.Blocked \|\| Sphere(s, acc.Ray) is {} h && h.Distance < acc.Distance, ...))`. | n/a | Functional could ship state-passing `Any`/`All`/`Aggregate` helpers for `ImmutableArray`, so the fast form is also the readable one. |
| 4 | Performance trap the lint steers toward | AGENTS.md says "`list.Add(x)` returns a new list: always use the result". FP0012 says the same. Taken literally for a pixel buffer, that becomes `Range(0, n).Aggregate(ImmutableArray<byte>.Empty, (acc, i) => acc.Add(...))`, which is O(n²). For the 230,400-byte image it took **3.5 s and allocated 26.5 GB**. `ImmutableList.Add` took 185 ms and 170 MB. `Select(...).ToImmutableArray()` took 0.87 ms. The lint is silent on all three. | Wrote: `Range(0, n*3).Select(i => ToByte(Channel(colours[i / 3], i % 3))).ToImmutableArray()`. | No. The guidance points toward the slow form. | Flag `Aggregate(ImmutableArray<T>.Empty, (acc, x) => acc.Add(...))` and suggest `Select(...).ToImmutableArray()`. Add a line to FP0005.md and FP0012.md: never build an `ImmutableArray` one `Add` at a time. |
| 5 | Performance: cold run | The optimisation took the warm render from 162 ms to 72 ms and allocations from 230 MB to 2.3 MB. A single cold run of the Cli stayed at about 0.44 s, because it is dominated by tier-0 JIT code (0.23 s with `DOTNET_TieredCompilation=0`). Code without loops gets no on-stack replacement, so the first calls to the recursive `Trace` run unoptimised until tiering catches up. | n/a | n/a | Worth one line in the docs. For short batch jobs, consider `<TieredPGO>` or ReadyToRun, or `TieredCompilation=false`. |
| 6 | FP0002: array element writes | `buffer[i++] = ToByte(c.R)` gives "'buffer[i++]' is changed here. Bind a new name or use a 'with' expression instead." ## What worked well

- AGENTS.md plus the rule docs were enough to write about 370 lines of core code that passed the lint on every check, without one fix. The one-screen summary is the right size.
- `readonly record struct` with operators for `Vec3`, `Colour` and `Ray` costs nothing at run time. Vector maths reads naturally and allocates nothing.
- The lint never got in the way of making things fast. Every optimisation I needed (static lambdas, tuple accumulators, `ImmutableArray.Aggregate`, index-based `Select`) was allowed, and there was no need for `#pragma` or an adapter.
- Thread splitting falls out of purity: `RenderRows(scene, range)` is a pure function, so the Cli's `Parallel.For` gives byte-identical output for any thread count, with no locks.
- `heal.sh --check` includes compiler errors, puts `[auto-fixable]` on each line, and runs in about 5 s, which is fast enough for a per-edit hook.
- The probe's auto-fixes (`readonly record struct`, `static class`, `init`) were the edits I would have made, apart from #9.
