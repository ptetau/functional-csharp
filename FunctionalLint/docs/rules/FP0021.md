# FP0021: Hash-based collections have no order

A hash set or dictionary (`ImmutableHashSet`, `ImmutableDictionary`, `HashSet`, `Dictionary`, frozen and concurrent ones) keeps its items in hash order. Using that order is reported:
- `string.Join` and `string.Concat` over one, or over its `Keys` or `Values`;
- copying one to a list or array (`ToImmutableArray`, `ToList`, `[.. set]`);
- `First`, `Last`, `ElementAt`, `Take`, `Skip`, `Zip`, `SequenceEqual` and similar.

It follows the order through steps that keep it (`Select`, `Where`, `SelectMany`, `Distinct`, `GroupBy`...). Sorting (`OrderBy`, `Order`) gives the items an order, so anything after it is fine. So is anything that doesn't care about order: `Count`, `Any`, `Sum`, `Contains`, `Max`, or building another set or dictionary.

## Why

Hash order isn't defined, and for strings it changes every run: .NET hashes strings with a random seed. Code that shows a set in its own order gives different output each time, which makes tests flaky and diffs noisy. The sample library's `ValueMap.ToString` did exactly this until this rule found it.

## Instead

Before:

```csharp
public static string Tags(ImmutableHashSet<string> tags) => string.Join(", ", tags);
```

After:

```csharp
public static string Tags(ImmutableHashSet<string> tags) => string.Join(", ", tags.Order(StringComparer.Ordinal));
```

Or keep the items in an `ImmutableSortedSet` or `ImmutableSortedDictionary`, which have an order.

## Auto-fix

None. Which order to sort by is up to you.
