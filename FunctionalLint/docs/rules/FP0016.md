# FP0016: Checks must stay on

A functional core can't turn its checks off. Inside a file, the build reports:

- `#pragma warning disable` (with or without rule IDs);
- `[SuppressMessage]` and `[UnconditionalSuppressMessage]`, including `[assembly: ...]` ones in `GlobalSuppressions.cs`, and under another name (`using Quiet = ...SuppressMessageAttribute;`);
- `#nullable disable`.

The gate (`heal.sh --check`, the agent hook and CI) runs the same scan itself, because in the build a pragma can switch FP0016 off too. Under a policy (`functionallint.policy`, see the README) it also reports what no file shows:

- a rule lowered below `error` by `<NoWarn>`, an `.editorconfig` or `.globalconfig` (`dotnet_diagnostic.FP0001.severity = none`), or a bulk setting for the `Functional` category;
- the same for the compiler checks and culture rules `FunctionalCore.props` makes errors: CS8509 (a switch that misses a case), the nullable warnings (CS8600 and the rest), and CA1304, CA1305, CA1309, CA1310 and CA1311;
- CS8509 or the nullable warnings no longer errors, because `TreatWarningsAsErrors` and the props file's `WarningsAsErrors` were taken away;
- nullable checking turned off for the project (`<Nullable>disable</Nullable>`);
- `RunAnalyzers` or `RunAnalyzersDuringBuild` set to anything but `true`, in the project or a file it imports. The build would then run no analyzers at all;
- code marked as generated, which every analyzer skips, so the build can't report it: `[GeneratedCode]` on a type or member, lines after `#line hidden`, or a whole file: an `<auto-generated>` comment at the top, a name like `Prices.g.cs` or `Prices.designer.cs`, or `generated_code = true` (files under `obj/` are left alone);
- another `functionallint.policy` between the project and the repository root. The build uses the nearest one, so it would replace the owner's rules there;
- a project the policy lists as a core that no longer imports `FunctionalCore.props`. The gate still checks it with every rule.
- a source generator in a core, other than .NET's own (from the SDK or a reference pack): the code it writes isn't the project's own source, so nothing checks it. The policy can allow one by name in `functional_lint.allowed_references`.

The project owner can allow exceptions with `functional_lint.may_lower` in the policy: rule IDs (any, not just FunctionalLint's) and `nullable`, which covers every nullable warning. A blanket `#pragma warning disable` with no IDs is never allowed.

If `FUNCTIONALLINT_POLICY` names a policy file that doesn't exist, the gate stops with exit 2 instead of checking without it.

## Why

Every other rule is only as strong as the easiest way to switch it off. An agent stuck on a rule will reach for a pragma or a config setting if nothing stops it, and the code then looks clean when it isn't.

## Instead

Fix what the rule reports, using its message. If a rule really can't apply somewhere, that's the owner's call: they add it to `functional_lint.may_lower` in the policy.

Before:

```csharp
#pragma warning disable FP0001
public static int Total(IReadOnlyList<int> xs) { var t = 0; foreach (var x in xs) t += x; return t; }
#pragma warning restore FP0001
```

After:

```csharp
public static int Total(IReadOnlyList<int> xs) => xs.Sum();
```

## Auto-fix

None. Removing the suppression is easy, but fixing what it hid isn't.
